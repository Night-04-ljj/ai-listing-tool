# AI Listing 工具（Amazon 多站点）

![Python](https://img.shields.io/badge/Python-3.10%2B-blue)
![Dependencies](https://img.shields.io/badge/dependencies-0-brightgreen)
![Platform](https://img.shields.io/badge/platform-Windows%20%7C%20macOS%20%7C%20Linux-lightgrey)

面向跨境电商自有品牌的**商品详情页文案（Listing）生成工具**：产品参数表进 → 多语言合规文案出。

核心是一条闭环：**生成 → 平台规则校验 → 定点修复 → 兜底裁剪**。
生成不难，难的是**让输出的东西运营敢直接用**。

**不想跑代码，只想看效果？**
[生成结果样例](docs/example-listings.md) ｜ [评测报告](docs/eval-report.md) ｜ [与真实在售文案的对比](docs/compare-report.md)

> 上面几份是 `output/` 里的真实产物（`output/` 本身不进版本库）。
> 克隆下来之后**填一个自己的 API Key 就能重新生成**；不填也能跑离线自测。

---

## 特性

| | |
|---|---|
| **多站点** | US / UK / DE / JP，语言与站点规则分离配置；每站独立的字符上限、用词习惯、关键词库 |
| **规则校验** | 12 类平台规则代码化：字符数、禁用词、全大写、emoji、禁用字符、第三方品牌、条数、重复、搜索词字节数、关键词堆砌…… |
| **定点修复** | 发现违规后把**具体哪一条、违反哪条规则**回喂给模型重写，而不是笼统地"重新生成" |
| **兜底裁剪** | 模型若干轮仍不听话时，用确定性规则裁剪（截断超长、补齐条数），保证一定有可交付结果 |
| **批量** | 产品表进 → 每站点一个固定名 CSV 出，Excel 直接打开 |
| **网页界面** | 零依赖本地 Web 应用：多语言并排对比、批量进度条、临时产品、产品表导入、统计看板、导出 |
| **评测** | 合规率、词级关键词覆盖率、平均修复轮数、Badcase 归因 |
| **基准对比** | 把 AI 生成的标题和**真实在售 Listing 标题**做结构化对比（长度 / 结构 / 实词覆盖率） |
| **零第三方依赖** | 只用 Python 标准库。不需要 `pip install`，不需要虚拟环境，装了 Python 就能跑 |

## 它解决什么问题

跨境卖家一个新型号要在多个站点上架，标题、五点描述、长描述、后台搜索词乘以语种，
就是几十份文案。人工写一份要几十分钟，而且每个平台都有一堆字符限制和禁用词，
写错了会被拒审甚至下架。

这个工具把这段流程做成批处理：**产品参数填一次，多站点文案一起出，并且逐条过了平台规则校验。**

## 为什么不用 RAG / LangChain

这是本项目最重要的一个设计判断。

| 这个场景真正需要的能力 | RAG 能提供吗 | 本项目的解法 |
|---|---|---|
| 输入是**结构化产品参数**（型号 / 承重 / VESA / 尺寸） | ❌ RAG 面向的是非结构化文档检索 | 直接把参数渲染进 Prompt |
| 输出必须**严格遵守平台规则** | ❌ RAG 完全不管输出约束 | 自建 Schema + 规则校验器 + 定点修复 |
| 品牌语气、卖点库、关键词库（几十到几百条） | ⚠️ 可以，但属于杀鸡用牛刀 | 全量写进 Prompt |
| 参考几个优秀 Listing 范例 | ⚠️ 可以，但没必要 | few-shot 放 1 条范例 |
| 批量跑几百个 SKU 并保证可交付 | ❌ RAG 不解决 | 批量流水线 + 兜底裁剪 |

**一句话**：Listing 生成的核心矛盾不是「知识找不到」，而是「**模型不听话**」——
它会超字符、会写促销词、会编造参数。所以关键投入应该放在**输出约束**上，而不是检索上。

**什么时候才需要引入检索？** 当关键词库涨到几千条、品牌规范有几十份文档、
Prompt 装不下或 token 成本压不住的时候。到那时也应该先试「按类目过滤 + 关键词匹配」，
而不是直接上向量库。**技术选型看的是维护成本，不是流行度。**

## 快速开始

### 环境要求

- Python **3.10 或更高**（`python --version` 或 `py --version` 检查）
- 一个 OpenAI 兼容接口的 API Key
- 除此之外**什么都不用装**

### 1. 获取代码

```bash
git clone https://github.com/Night-04-ljj/ai-listing-tool.git
cd ai-listing-tool
```

或者直接下载 ZIP 解压。

### 2. 配置

复制模板并填 Key：

```bash
copy .env.example .env        # Windows
cp .env.example .env          # macOS / Linux
```

打开 `.env`，在 `LLM_API_KEY=` 后面填上你的 Key（**不要加引号或空格**）。

默认走 DeepSeek。想换服务商就改这两行，任何 OpenAI 兼容接口都行：

```ini
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
```

<details>
<summary>其他服务商配置示例</summary>

```ini
# 通义（阿里云百炼）
LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_MODEL=qwen-plus

# 硅基流动
LLM_BASE_URL=https://api.siliconflow.cn/v1
LLM_MODEL=deepseek-ai/DeepSeek-V3

# 本地 Ollama
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen2.5:14b
```

</details>

> **懒人做法**：直接运行 `python start.py`，它会**自动**从 `.env.example` 生成 `.env`
> 并提示你去填 Key，不用手动复制。

### 3. 运行

**方式一：交互式菜单（推荐新手）**

```bash
python start.py          # macOS / Linux
py start.py              # Windows
```

Windows 也可以直接双击 `启动.bat`。

菜单里可以：离线自测、看 SKU 列表、生成单条、批量生成、跑评测、打开网页界面、看结果仓库统计。

**方式二：命令行**

```bash
python selftest.py                                    # 离线自测（不花钱）
python generate.py --list                             # 看有哪些 SKU
python generate.py --sku S02M1225B --site US          # 生成一条
python batch.py --site US --site DE                   # 批量生成
python evaluate.py                                    # 评测
python compare.py                                     # 与真实在售文案对比
python web.py                                         # 打开网页界面
```

**方式三：网页界面**

```bash
python web.py            # 浏览器自动打开 http://127.0.0.1:8765
python web.py --port 9000 --no-browser    # 换端口 / 不自动开浏览器
```

### 不用 API Key 能做什么

```bash
python selftest.py       # 规则引擎的 11 个离线用例，不联网、不花钱
```

网页界面也能正常打开，只是点生成时会提示需要配置 Key。
`docs/` 目录里有生成结果样例，不用跑代码就能看效果。

## 使用说明

### 产品表格式

`data/products.csv` 是产品表，一行一个 SKU。示例（15 列）：

```csv
sku,brand,model_name,product_type,category,tv_size_range,max_load_kg,vesa_range,material,color,mount_type,wall_types,features,package_includes,target_keywords
S02M1225B,FITUEYES,Master V2 FT48,Floor TV stand with wheels,tv_stand,24-48 inch,35,75x75 mm to 200x200 mm,,Black,...
```

| 列 | 是否必需 | 说明 |
|---|---|---|
| `sku` | **必需** | 唯一标识（大小写不敏感） |
| `category` | 可选 | 决定用哪套关键词库（如 `tv_stand`）。没有或不在词库里 → 关键词留空，让模型按目标语言自己选 |
| `target_keywords` | 可选 | 用 `;` 分隔，手填后**覆盖**关键词库 |
| 其他列 | 可选 | 会**原样**进 Prompt 作为产品参数 |

### 产品表可以完全是你自己的格式

**不需要和上面的示例列一致。** 中文表头也认：

| 行为 | 说明 |
|---|---|
| 认识的英文列名 | 映射成中文标签（`max_load_kg` → `最大承重(kg)`） |
| 不认识的列名 | **原样保留**进 Prompt（`产品名称`、`主要卖点`、`承重` 都能用） |
| `sku` / `category` / `target_keywords` | 内部字段，不放进 Prompt |
| 空的字段 | 跳过，不会进 Prompt——**参数没给，模型就不写，避免编造** |

> 换句话说：**拿到一张真实的产品表就能直接跑**，不用先改成这里的格式。

### 批量生成

```bash
python batch.py --site US --site DE            # 两个站点
python batch.py --site US --sku S02M1225B      # 只跑一个 SKU
python batch.py --site US --timestamp          # 额外留一份带时间戳的历史文件
```

产出物：

```
output/
  all_listings.json     所有结果，键 = "SKU|站点"（覆盖式写入，不会重复堆积）
  all_listings.md       人类可读汇总，一个 SKU 一节
  listings_US.csv       运营交付物（固定文件名，Excel 直接打开）
  listings_DE.csv
  eval_report.md        评测报告
  compare_report.md     与真实在售文案的对比
  llm_cache/            大模型响应缓存
```

需要把单独一条发给别人时加 `--split`：

```bash
python generate.py --sku S02M1225B --site US --split
```

### 评测

```bash
python evaluate.py                        # 控制台输出 + output/eval_report.md
python evaluate.py --out my_report.md     # 指定报告输出路径
```

评测是**纯离线**的，读的是 `output/all_listings.json`，不调用模型、不花钱。
指标定义见下方[实测数据](#实测数据)一节。

> 用 LLM 给文案打质量分（LLM-as-a-Judge）还没做，见「路线图」。

### 与真实在售文案对比

`data/benchmark.json` 里存**真实在售的 Listing 标题**（含来源链接）。跑：

```bash
python compare.py
```

会输出每条的：真实标题 vs AI 标题、长度对比、结构差异（品牌前置 / 含尺寸 / 含承重 / 含 VESA / 含颜色）、
实词覆盖率、以及漏掉了哪些词。

**想加基准**：打开 `data/benchmark.json`，照着格式把真实标题粘进 `title` 字段即可。
亚马逊对爬虫拦截很严，正文（五点描述）拿不到，但**标题能拿到，而且标题本身就是 SEO 优化的产物**。

### 网页界面

`web.py` 是一个**零依赖的本地 Web 应用**（标准库 `http.server`，没有 Flask / Streamlit）：

| 功能 | 说明 |
|---|---|
| 选产品 + 多选语言 | 语言可多选，生成后**并排对比**（同一 SKU 的 US / DE / JP 放一起看） |
| 生成 / 批量生成 | 前端逐个调用，带真实进度条；同样的内容第二次跑命中缓存，不花钱 |
| **临时产品** | 粘贴任意参数直接生成，**不写进产品表**——试新品、临时来个新型号时很方便 |
| **产品表导入** | 上传 CSV 替换产品表，**立即生效不用重启**；自动识别 UTF-8 / GBK；旧表自动备份，一键恢复 |
| 卡片展示 | 标题 / 五点的实时字符数、搜索词的字节数，一眼看出离上限还有多少 |
| 合规面板 | 每条显示修复轮数、error / warning 明细、兜底裁剪记录 |
| 统计看板 | 总条数、合规率、各站点关键词覆盖率、缓存调用次数 |
| 导出 | 一键下载汇总 md、某站点的 CSV、当前产品表（可当模板） |

**临时产品的两种写法可以混着写**：

```
型号: XG-200
承重: 75kg
VESA: 200x200 至 800x500 mm

适用于 40 到 90 英寸电视，安装前请确认墙体为混凝土或实心砖墙。
```

会被解析成 **6 个结构化参数 + 1 段补充说明**，两种都喂给模型。
判定规则很保守（键要短、不能有空格、不能是网址），宁可当成自由文本，
也不要把一句话错误地拆成一堆参数名。

**停止服务**：回到命令行窗口按 `Ctrl + C`。

## 设计决策

| 决策 | 理由 | 备选方案与放弃原因 |
|---|---|---|
| **不用 RAG / LangChain** | 输入是结构化参数，瓶颈在输出约束而非知识检索 | 引入向量库和框架会带来不必要的运维与调试成本 |
| **不用 openai SDK，用标准库 urllib** | SDK 为了一个 POST 带进 12 个传递依赖（httpx / anyio / sniffio…），依赖越多安装越容易失败；报错信息也能自己控制 | 用 SDK：少写 20 行，但多 12 个包，401 时只给一堆堆栈 |
| **零第三方依赖** | 依赖越少，`pip install` 卡住或失败的机会越少；任何装了 Python 的机器都能直接跑 | 引入 SDK / 框架：装不上就跑不起来 |
| **自建 Schema 校验，不用 Pydantic** | 模型会加解释、会用 markdown 包裹，直接 `json.loads` 会崩；字段缺失或类型错也要能拦住并触发重写 | 用 Pydantic：多 4 个依赖，而这里只有 4 个字段 |
| **自写 .env 解析器** | 15 行就够，省掉 python-dotenv 这个依赖 | 用 python-dotenv：又少一个装不上的理由 |
| **把具体违规项回喂给模型** | 只说"重新生成"，模型会再犯同样的错；说清哪条违规、违反哪条规则，一次改对的概率高得多 | 不做修复、靠人工改，等于没提效 |
| **保留确定性兜底裁剪** | 不能因为"模型这轮不听话"整个任务失败 | 无限重试：成本不可控 |
| **结果写进一个文件，按 (SKU, 站点) 覆盖** | 一条文案两个文件 → 100 个 SKU 就是 800 个文件。用追加会重复堆积，所以用键值覆盖 + 原子写入（数据量小，整体重写成本可忽略，换来天然去重） | 一条一个文件：没法管理；追加到 jsonl：重跑一次就多一条重复记录 |
| **CSV 固定文件名** | 每次跑都新增一个带时间戳的文件是另一种"文件爆炸"；需要留历史时加 `--timestamp` | 永远带时间戳：文件夹里全是同一天的副本 |
| **CSV 用 `utf-8-sig`** | Excel 双击打开不乱码 | 普通 utf-8：中文列头在 Excel 里变乱码 |
| **导入产品表支持任意表头** | 真实产品表的列名一定和示例不一样。只认固定列名的话，导入后会得到空参数，模型就开始编，而且不报错 | 要求用户改成固定格式：多一道门槛，真实数据也很难改 |
| **缺关键词时传空列表，而不是回退到英文** | 英语站点之间回退没问题；但把英文关键词塞进德语 / 法语 Listing 会静默毁掉文案质量，且难以发现 | 一律回退到 US：加一个非英语站点就出问题 |
| **覆盖产品表前留两级备份** | 只有一级 `.bak` 时，连续导入两次会把原始表弄丢（第二次覆盖了 `.bak`）。现在保留「上一版 + 3 份历史快照」，且快照名保证唯一 | 只留一个 `.bak`：连续误操作不可恢复 |
| **平台规则集中可配置** | 平台规则会变，代码不应该跟着改 | 硬编码：规则一改就要改代码 |
| **缓存大模型响应** | 改规则重跑不重复付费；网络不可用时也能继续开发和演示 | 不缓存：每轮调试都烧钱 |

## 关键实现说明

### 关键词覆盖率为什么是「词级」而不是「整短语匹配」

最早用的是**整短语原文匹配**：把 `heavy duty tv wall mount` 当一个字符串去正文里找。
结果是 **12%**，看起来文案质量很差。

但把文案摊开一看，`heavy`、`duty`、`wall`、`mount` **全都写进去了**，
标题里就有 `Heavy Duty ... Bracket` 和 `TV Wall Mount`。
**问题不在文案，在指标本身** —— 搜索引擎按词（含词干）匹配，
不会要求你原样输出整个长尾短语。

改成**词级覆盖**：关键词里每个实词出现在正文中的比例，再对所有关键词取平均。

### 分词必须是 Unicode 感知的

同一个坑还有第二层：分词正则最初写的是 `[a-z0-9]+`，**只认 ASCII 字母**。
德语 `Ständer` 里的 `ä` 不在范围内，所以被从中间切成了 `st` + `nder`。
而 `st` 这种两字母碎片几乎能匹配任何文本，**导致覆盖率被系统性高估**。

修成 Unicode 感知之后（`[^\W_]+`），德国站的数字从 67% 掉到 59%——
不是结果变差了，是**结果变对了**。

> 这两次都指向同一件事：**度量工具本身有 bug 时不会报错，
> 只会给你一个看起来合理的错误数字。**

## 实测数据

### 合规与覆盖率

> 当前样本：**9 个 SKU，已生成 7 条**（US 3 / UK 2 / DE 2）。样本量还很小，
> 扩充之后重新跑 `evaluate.py` 即可刷新。

| 指标 | 数值 |
|---|---|
| 首轮即合规率 | **85.7%**（US 100% / UK 100% / DE 50%） |
| 最终合规率 | **100%**（7/7） |
| 平均修复轮数 | **1.14** |
| 长度合规率 | **100%**（标题 / 五点 / 描述均在字符上限内） |
| 搜索词字节合规率 | **100%**（后台搜索词 ≤ 250 字节） |
| 目标关键词覆盖率（词级） | **US 96.0% / UK 89.2% / DE 73.3%** |
| 关键词全词命中率 | **US 85.2% / UK 61.1% / DE 45.0%** |
| 残留禁用词 | **0**（硬指标，必须为 0） |
| 单条成本 | **未统计**（工具目前不记录 token 用量，见「已知不足」） |

**德语的数字明显低于英语**（73.3% vs 96.0%），原因有两个，都是可解释的：

1. 德语长尾复合词更难自然融入文案
2. 覆盖率算的是**词形**而不是**语义**：真实标题写 `Rollbar`，模型写 `mit Rollen`；
   真实写 `Wohnung`，模型写 `Wohnzimmer`。这是合理的同义选择，但会被算成"漏掉"

所以 **73.3% 是下限估计**，实际表现比这个数字好。

### 与真实在售文案的对比

合规率只能说明"没违规"，说明不了"写得好不好"。
所以 `compare.py` 把 AI 生成的标题和**真实在售的标题**做结构化对比
（基准在 `data/benchmark.json`，含来源链接）。

**第一次对比就发现了一个系统性问题：**

| 样本 | 真实在售 | AI（改前） | 差距 |
|---|---|---|---|
| Master V2 FT48 · DE | 182 字符 | 110 字符 | **短 40%** |
| Eiffel 75-100 · DE | 189 字符 | 144 字符 | 短 24% |
| Eiffel 32-75 · US | 142 字符 | 94 字符 | 短 34% |

AI 标题系统性偏短，而且漏掉了三样东西：**系列名**（Master Serie / Eiffel Serie）、
**使用场景**（Wohnung Büro Heim）、**部分功能**（Kabelmanagement）。

根因是 Prompt 里只写了"**不超过** 200 字符"——**只给了上限，没给目标**，
模型写完要点就停了。而真实运营会把字符额度用满，因为那都是搜索权重。

**针对这个发现改了四处：**

1. "不超过 200 字符" → "**目标为上限的 90%~93%**"
2. 参数里有系列名或型号，**必须写进标题**
3. **至少写一个使用场景**
4. 德语标题习惯用 `|` 分隔卖点组（从真实标题里观察到的），写进 `SITE_RULES["DE"]["title_style"]`

**改进前后：**

| 样本 | 真实长度 | AI 改前 | AI 改后 | 覆盖率 改前 → 改后 |
|---|---|---|---|---|
| Master V2 FT48 · DE | 182 | 110 | **180** | 58% → **67%** |
| Eiffel 75-100 · DE | 189 | 144 | **175** | 59% → **67%** |
| Eiffel 32-75 · US | 142 | 94 | **147** | 62% → **69%** |
| **平均** | **171** | **116** | **167** | **60% → 68%** |

标题长度从"平均短 32%"变成"基本追平"，实词覆盖率提升 8 个百分点。

> ⚠️ **这个结论的局限**：只对比了 3 条真实标题，样本太小，说明不了市场规律。
> 要下结论至少需要 10–20 条。目前只能说"发现了这个现象"。

### 建议做的对照实验

1. `MAX_REPAIR_ROUNDS = 0` vs `2` → 量化"定点修复"带来的合规率提升
2. 规则表述写在 System Prompt 里 vs 只放在校验器里 → 看首轮通过率差多少

## 数据来源与真实性

为了让示例数据可追溯，这里说明清楚哪些是真实数据、哪些是示例。

| 内容 | 来源 |
|---|---|
| 产品型号与参数（`data/products.csv`） | ✅ **真实数据**，来自 FITUEYES 官方站点（[eu.fitueyes.com](https://eu.fitueyes.com/) / [fitueyes.com](https://fitueyes.com/)）商品页与亚马逊在售页 |
| 关键词库（US / UK 的 `tv_stand` 类目） | ✅ **真实数据**，取自官方商品页的 `tags` 字段 |
| 关键词库（DE 的 `tv_stand`） | ✅ 从 Amazon.de 真实在售标题中提取的词组 |
| 关键词库（其他类目 / JP） | ⚠️ 按常见说法起草，**需要用亚马逊后台搜索词报告校准** |
| 真实在售基准（`data/benchmark.json`） | ✅ 真实标题，每条都带来源链接 |
| `data/products.sample.csv` | ❌ 早期编写的示例数据，仅作对照保留 |
| `brand_guide.json` 的品牌调性 | ⚠️ 按这类产品的常见写法起草，**不是品牌方真实的品牌手册** |

### ⚠️ 一处数据存疑

Master V2 FT48 的承重，两处来源不一致：

- 官方站商品描述写的是 **10.3 kg**（`una portata di 10,3 kg`）
- 亚马逊德国站在售页标题写的是 **最多 35 kg**（`35 kg'a kadar`）

`products.csv` 里暂按 **35 kg** 填写（更接近这类支架的常理，10.3 kg 可能是产品自重），
**但使用前建议在官方规格表上核对**。

### 一个值得记下的教训

项目最初编写过一个叫 `FT48-B` 的"固定式电视挂架"作为示例。
后来查证发现：**真实的 FT48 是"带轮子的落地电视支架"**（Master V2 FT48，24–48 寸），
产品形态完全不同。

**这就是为什么示例数据必须标注来源** —— 参数错了比没有参数更糟。
（`products.sample.csv` 里保留了那份早期示例数据，仅作对照。）

## 已知不足

1. **文案的说服力 / 可读性没有客观指标。** 合规是机器能判的，但"写得好不好"只能人工抽检。
   要量化需要找运营盲评，或做 LLM-as-a-Judge 的相对排序。
2. **关键词覆盖率只判实词是否出现**，判不了"是否自然、是否堆砌、语义是否准确"。
   而且它是**词形匹配**，会把 `Rollbar` 和 `mit Rollen` 当成不同词。
3. **warning 级问题不会自动修复。** 例如「后台搜索词与标题重复」，`evaluate.py` 会告警，
   但模型不会因此重写——因为 warning 需要人工判断。其实这一类完全可以规则化自动重写。
4. **不记录 token 用量**，所以没有成本数据。对于一个要算 ROI 的工具来说这是明显的缺口。
5. **平台规则会变**，`rules.py` 需要定期按卖家后台核对，不能一劳永逸。
6. **没有接真实的亚马逊接口**（SP-API），目前是离线生成、人工上传。

## 路线图

按性价比排序：

1. **记录 token 与成本** —— "单条几分钱"是业务方最关心的一句话，现在没有数据支撑
2. **反向校验** —— 把已上线的 Listing 抓回来跑一遍规则校验，找出历史违规
3. **warning 自动修复** —— 把「搜索词与标题重复」这类可规则化的问题改成自动重写
4. **A/B 关键词版本** —— 同一 SKU 生成两版标题，投广告测点击率，用数据反推哪版更好
5. **扩展站点** —— 加 FR / IT / ES（但需要先有真实的当地关键词，否则会埋雷）
6. **接入评论数据做卖点排序** —— 把好评里出现最多的卖点排到五点描述的前两条
7. **A+ 页面与广告文案** —— 同一份参数可以喂给多个模板，边际成本几乎为零
