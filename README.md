# AI Listing 工具（Amazon 多站点）

> 面向**跨境电商自有品牌**的商品详情页文案生成工具：产品参数表进 → 合规文案出。
> 纯 Python + 大模型 API，**不使用 RAG、不使用 LangChain**，也**不需要向量数据库**。

**不想跑代码，只想看效果？** → [生成结果样例](docs/example-listings.md) ｜ [评测报告](docs/eval-report.md) ｜ [与真实在售文案的对比](docs/compare-report.md)

> 上面三份是用 `output/` 里的真实产物复制过来的（`output/` 本身不进版本库）。
> 克隆下来之后，**只要填一个自己的 API Key 就能重新生成**；不填也能跑离线自测。

### ⚠️ 一个必须知道的纠正

我最早编了一个叫「**FT48-B**」的"固定式电视挂架"。后来查证发现：
**真实的 FT48 是「带轮子的落地电视支架」**（Master V2 FT48，24–48 寸）——
产品形态完全不同。

**这正是为什么不能拿编的数据当事实讲。** 现在 `products.csv` 里的三个 SKU：

| SKU | 型号 | 说明 |
|---|---|---|
| `S02M1225B` | Master V2 FT48（黑色） | 真实 SKU，参数来自官方商品页 |
| `S02M1224A` | Master V2 FT48（白色） | 同款白色变体 |
| `F82F2461B` | Eiffel F82F2461B | 参数较少，**故意留空 VESA 和包装清单**，用来验证"参数没给就不编" |

### ⚠️ 一处存疑，别当事实讲

Master V2 FT48 的承重，两处来源不一致：

- 官方站商品描述写的是 **10.3 kg**（`una portata di 10,3 kg`）
- 亚马逊德国站在售页标题写的是 **最多 35 kg**（`35 kg'a kadar`）

我按 35 kg 填了（更接近这类支架的常理，10.3 kg 可能是**产品自重**或翻译问题），
**但这一点务必在官方规格表上核对。**建议的处理方式是：

> "承重这一项我在官网描述和亚马逊在售页上看到的数字不一致，我暂时按 35kg 填的，
> 但没有拿它当定论——因为参数错了比没有参数更糟。"

**把"这里我不确定"写进文档，比假装确定安全得多。**

## 一、为什么这个场景不需要 RAG 和 LangChain

这是本项目最重要的一个设计判断。理由如下：

| 这个场景真正需要的能力 | RAG 能提供吗 | 我用什么解决 |
|---|---|---|
| 输入是**结构化产品参数**（型号/承重/VESA/尺寸） | ❌ RAG 面向的是非结构化文档检索 | 直接把参数渲染进 Prompt |
| 输出必须**严格遵守平台规则**（字符数、禁用词、条数） | ❌ RAG 完全不管输出约束 | **自建 Schema + 规则校验器 + 定点修复** |
| 品牌语气、卖点库、关键词库（几十到几百条） | ⚠️ 可以，但属于杀鸡用牛刀 | **全量写进 Prompt** |
| 参考几个优秀 Listing 范例 | ⚠️ 可以，但没必要 | **few-shot 放 1 条范例** |
| 批量跑几百个 SKU 并保证可交付 | ❌ RAG 不解决 | 批量流水线 + 兜底裁剪 |

**一句话结论：**

> Listing 生成的核心矛盾不是「知识找不到」，而是「**模型不听话**」——
> 它会超字符、会写促销词、会编造参数。所以关键投入应该放在**输出约束**上，而不是检索上。

**那什么时候才需要引入检索？**
当关键词库涨到几千条、品牌规范有几十份文档、Prompt 装不下或 token 成本压不住的时候。
到那时我会先考虑「按类目过滤 + 关键词匹配」这种最简方案，而不是直接上向量库。
**技术选型看的是维护成本，不是流行度。**

## 二、架构

```
                    ┌──────────────── 离线知识（不检索，直接进 Prompt）─────────────┐
                    │  data/brand_guide.json   品牌调性、卖点、写作要求            │
                    │  data/keywords.json      各站点的目标关键词库                │
                    │  prompts.EXAMPLE         一条合规范例（few-shot）            │
                    └──────────────────────────┬──────────────────────────────────┘
                                               │
  data/products.csv  ──►  读产品参数            ▼
   (批量：几百个 SKU)      product_facts()   build_system_prompt() + build_user_prompt()
                                               │
                                               ▼
                                        ┌─────────────┐
                                        │  大模型 API  │  （JSON 模式输出）
                                        └──────┬──────┘
                                               ▼
                                     Schema 校验（脏数据进不来）
                                               │
                                               ▼
                          ┌──────────── rules.py + schema.py ────────────┐
                          │  字符数 / 禁用词 / 全大写 / emoji / 禁用字符  │
                          │  第三方品牌 / 条数 / 重复 / 搜索词字节 / 关键词│
                          └───────────────────┬──────────────────────────┘
                                              │
                        有 error 违规？────────┤
                          │ 是                  │ 否
                          ▼                     ▼
       把「具体违规项」回喂给模型重写       ✅ 交付
       （最多 MAX_REPAIR_ROUNDS 轮）
                          │
                          │ 仍然不过
                          ▼
              autocorrect() 确定性兜底裁剪
              （截断超长 / 补足条数）→ ✅ 保证有可交付结果
```

**核心是那个闭环：生成 → 校验 → 定点修复 → 兜底。** 没有这个闭环，工具输出的东西运营是不敢直接用的。

## 三、快速开始

> **零依赖**：不需要 `pip install`，不需要虚拟环境，不需要联网装东西。
> 有 Python 3.10+ 就能跑。双击 `启动.bat`（或 `py start.py`）即可。

### 第一次运行要准备什么

**只需要一样东西：一个你自己的大模型 API Key。其他什么都不用改。**

1. 运行 `py start.py`（或双击 `启动.bat`）—— 它会**自动**从 `.env.example` 生成 `.env`
2. 打开 `.env`，在 `LLM_API_KEY=` 后面填上你的 Key
3. 再运行一次，按菜单操作

**没有 Key 也能做的事**：`python selftest.py` —— 规则引擎的 11 个离线用例，不联网、不花钱。
网页界面也能打开，只是点生成会提示需要配置 Key。

**想换服务商**：改 `.env` 里的 `LLM_BASE_URL` + `LLM_MODEL` 就行，
任何 OpenAI 兼容接口都能用（DeepSeek / 通义 / 硅基流动 / OpenAI / 本地 Ollama）。

```bash
# 1. 不需要装任何东西！
#    本项目零依赖，只用 Python 标准库。
python --version     # 或 py --version

# 2. 配置密钥
copy .env.example .env        # Mac/Linux: cp
# 编辑 .env，填入 LLM_API_KEY

# 3. 先跑离线自测（不花钱，验证规则引擎）
python selftest.py

# 4. 看有哪些 SKU
python generate.py --list

# 5. 生成单个 SKU
python generate.py --sku S02M1225B --site US

# 6. 生成德语站点
python generate.py --sku S02M1225B --site DE

# 7. 批量跑（产品表进，CSV 出，可直接发运营）
python batch.py --site US --site DE

# 8. 评测，产出可归档的评测报告
python evaluate.py

# 9. 打开网页界面（生成 / 多语言并排对比 / 统计 / 导出）
python web.py            # 浏览器自动打开 http://127.0.0.1:8765
```

### Web 页面

`web.py` 是一个**零依赖的本地 Web 应用**（标准库 `http.server`，没有 Flask / Streamlit）：

| 功能 | 说明 |
|---|---|
| 选产品 + **多选语言** | 语言可多选，生成后**并排对比**（同一个 SKU 的 US / DE / JP 放一起看） |
| 生成 / 批量生成 | 前端逐个调用，带**真实进度条**；同样的内容第二次跑命中缓存，不花钱 |
| **临时产品** | **粘贴任意参数直接生成，不写进产品表** —— 试新品、试别人的产品、临时要生成一个新型号、来不及先维护产品表时，也能立刻出文案 |
| **产品表导入** | 上传 CSV 即可替换产品表，**立即生效不用重启**；自动识别 UTF-8 / GBK（Excel 导出的中文 CSV 常是 GBK）；旧表自动备份，**一键恢复** |
| 卡片展示 | 标题/五点的**实时字符数**、搜索词**字节数**（对着上限看，一眼知道离超限还有多少） |
| 合规面板 | 每条显示修复轮数、error/warning 明细、兜底裁剪记录 |
| 统计看板 | 总条数、合规率、**各站点关键词覆盖率**、缓存调用次数 |
| 导出 | 一键下载 `all_listings.md`、某站点的 CSV、以及当前产品表（可当模板） |

#### 临时产品：两种写法可以混着写

```
型号: XG-200
承重: 75kg
VESA: 200x200 至 800x500 mm

适用于 40 到 90 英寸电视，安装前请确认墙体为混凝土或实心砖墙。
```

上面这种写法会被解析成 **6 个结构化参数 + 1 段补充说明**，两种都喂给模型。
判定规则很保守（键要短、不能有空格、不能是网址），宁可当成自由文本，
也不要把一句话错误地拆成一堆乱七八糟的参数名。

#### 产品表：字段可以完全不一样

导入的产品表**不需要和示例的 15 列一致**。中文表头也认：

| 行为 | 说明 |
|---|---|
| 认识的英文列名 | 映射成中文标签（`max_load_kg` → `最大承重(kg)`） |
| 不认识的列名 | **原样保留**进 Prompt（`产品名称`、`主要卖点`、`承重` 都能用） |
| `sku` / `category` / `target_keywords` | 内部字段，不放进 Prompt |
| 没有 `category` 或类目不在词库里 | 关键词传空，**让模型按目标语言自己选**，而不是塞英文进去 |

> 这一点很重要：**拿到公司真实的产品表就能直接跑**，不用先改成我的格式。

> **为什么不用 Flask/Streamlit**：这个项目坚持零第三方依赖，装不上包也能跑。
> 一个本地单人用的工具，标准库完全够用。**这与"零依赖"是同一个设计取舍。**

### 现场演示准备（重要）

如果要在**没有外网的环境**里演示，提前做这一步：

```bash
# 在家联网完整跑一遍（顺便让大模型响应缓存落盘）
python batch.py --site US --site DE

# 然后断网，启动网页 —— 缓存命中，生成秒出，界面照样能用
python web.py
```

看到页面顶部 `缓存 12 次` 并且生成请求瞬间返回，就说明稳了。

**为什么要这样准备：** 现场网络往往不可控（连不上外网、限速、要连他们的 WiFi 还要审批）。
缓存落盘后，你的整条链路可以在完全离线的状态下演示完 ——
**这是很多人现场演示时翻车的地方。**

另外记得把这几样东西拷到 U 盘 + 自己微信一份：

| 文件 | 用途 |

| `output/all_listings.md` | **人类可读汇总，一个 SKU 一节** —— 最直观的证据 |
| `output/listings_US.csv` | 用 Excel 打开，给运营看的那份 |
| `output/eval_report.md` | 数字，导成 PDF 或截图 |

## 四、目录说明

| 文件 | 作用 | 设计要点 |
|---|---|---|
| `rules.py` | 站点规则、禁用词表、品牌规范、关键词库 | "平台规则集中可配置，因为亚马逊的要求会变" |
| `schema.py` | 自建数据结构 + **规则校验器** + 兜底裁剪（零依赖） | "这是整个工具最值钱的部分" |

| `results.py` | **结果仓库**：所有结果写进一个文件，按 (SKU, 站点) 覆盖 | "避免一条文案两个文件，100 个 SKU 变成 800 个文件" |
| `batch.py` | 批量处理，产品表进 → CSV 出 | "运营手上是几百个 SKU 的表，单条生成没意义" |
| `evaluate.py` | 合规率、关键词覆盖率、修复轮数 | "这些数字就是从这来的" |
| `web.py` | **零依赖 Web 页面**（标准库 http.server） | "不用 Flask，因为这个项目坚持零依赖" |
| `selftest.py` | 离线测试规则引擎（不调用模型） | "校验是纯逻辑，可以离线测，不用烧额度" |
| `data/` | 品牌规范、关键词库、产品表、真实在售基准 | "换成公司真实资料就能用" |
| `docs/` | 生成结果样例、评测报告、对比报告 | 见文件开头的「不想跑代码，只想看效果」 |

## 五、关键设计决策

| 决策 | 为什么这么做 | 备选方案与放弃原因 |
|---|---|---|
| **不用 RAG** | 输入是结构化参数，不是文档检索问题 | 用向量库会引入不必要的运维和调试成本 |
| **不用 LangChain** | 流程是一条直线，框架只会让报错栈更深 | 框架适合复杂编排，这里没有多步决策 |
| **不用 openai SDK，用标准库 urllib 发 HTTP** | SDK 为了一个 POST 带进 12 个传递依赖（httpx/anyio/sniffio…），依赖越多安装越容易失败；而且报错信息我能自己控制 | 用 SDK：少写 20 行，但多 12 个包，401 时只给你一堆堆栈 |
| **自建 Schema 校验而不是直接 `json.loads`** | 模型会加解释、会用 markdown 包裹，直接 loads 会崩；字段缺失或类型错也要能拦住并触发重写 | 用 Pydantic：多 4 个依赖，而这里只有 4 个字段 |
| **零第三方依赖** | 依赖越少，`pip install` 卡住/失败的机会越少；**现场任何一台装了 Python 的机器都能直接跑** | 引入 SDK/框架：装不上就没法演示 |
| **结果写进一个文件，按 (SKU, 站点) 覆盖** | 一条文案两个文件 → 100 个 SKU = 800 个文件。用**追加**会重复堆积，所以用**键值覆盖 + 原子重写**（数据量小，整体重写成本可忽略，换来天然去重） | 一条一个文件：没法管理；追加到 jsonl：重跑一次就多一条重复记录 |
| **CSV 固定文件名，不再带时间戳** | 每次跑都新增一个文件是另一种"文件爆炸"；需要留历史时加 `--timestamp` | 永远带时间戳：文件夹里全是同一天的多个副本 |
| **关键词缺省时**传空列表让模型按语言自己生成** | 英语站点之间回退没问题；但**绝不能把英文关键词塞进德语/法语 Listing**，而且这种错不会报错、极难发现 | 一律回退到 US：加一个非英语站点就会静默毁掉文案质量 |
| **把违规项回喂给模型** | 只说"重新生成"，模型会再次犯同样的错；说清哪条违规、违反哪条规则，一次改对的概率高得多 | 不做修复，靠人工改，等于没提效 |
| **保留确定性兜底裁剪** | 线上不能因为"模型这轮不听话"整个失败 | 无限重试：成本不可控 |
| **Web 用标准库 http.server** | 本地单人工具，标准库够用，且保持零依赖；批量交给前端循环调用，能给出真实进度 | Flask/Streamlit：装不上就跑不起来 |
| **临时产品不写进产品表** | 试新品、试别人的产品是高频动作，不该污染正式产品库；生成结果也不进结果仓库，不污染统计 | 一律落库：产品表和统计很快就被测试数据塞满 |
| **导入产品表支持任意表头** | 公司的真实产品表列名一定和示例不一样。只认固定列名的话，导入后会得到**空参数**，模型就开始编，而且不报错 | 强制用户改成我的格式：多一道门槛，而且真实数据很难改 |
| **覆盖产品表前留两级备份** | 只有一级 `.bak` 的话，**连续导入两次就会把原始表弄丢**（第二次把 `.bak` 覆盖了）—— 我自己测试时踩到了。现在保留「上一版 + 3 份历史快照」，且快照名保证唯一（精确到秒会互相覆盖，也踩过） | 只留一个 `.bak`：连续误操作就不可恢复 |
| **规则集中可配置** | 平台规则会变，代码不该跟着改 | 硬编码：规则一改就要发版 |
| **CSV 用 `utf-8-sig`** | Excel 双击打开不乱码，运营会记住你 | 普通 utf-8：中文列头在 Excel 里变乱码 |
| **缓存大模型响应** | 改规则重跑不重复付费；**断网也能完整演示** | 不缓存：每轮调试都烧钱，现场断网就演不了 |

## 六、实测数据（含与真实在售文案的对比）

> ⚠️ 下面这些数字**必须你自己跑出来再填**。填假的，被追问"怎么测的"就会当场崩。

### 6.1 合规与覆盖率

> 当前样本：**5 个真实 SKU，已生成 3 条**（DE ×2、US ×1）。
> 样本量还很小，扩充之后记得重跑 `evaluate.py` 并更新本表。

| 指标 | 数值 | 怎么测的 |
|---|---|---|
| 样本量 | **7 条**（US 3 / UK 2 / DE 2） | `evaluate.py` |
| 首轮即合规率 | **85.7%**（US 100% / UK 100% / DE 50%） | `evaluate.py` 直接报 |
| 最终合规率 | **100%**（7/7） | `evaluate.py` |
| 平均修复轮数 | **1.14** | `evaluate.py` |
| 长度合规率 | **100%** | 标题/五点/描述均在字符上限内 |
| 搜索词字节合规率 | **100%** | 后台搜索词 ≤250 字节 |
| 目标关键词覆盖率（词级） | **US 96.0% / UK 89.2% / DE 73.3%** | `evaluate.py` |
| 关键词全词命中率 | **US 85.2% / UK 61.1% / DE 45.0%** | 所有实词都写进去了的比例 |
| 残留禁用词 | **0** | 硬指标，必须为 0 |
| 单条 Listing 成本 | **未统计** | ⚠️ 工具目前不记录 token 用量，这是已知不足，下一步要补 |

> **德语的数字明显低于英语**（73.3% vs 96.0%）：德语长尾复合词更难自然融入文案，
> 而且德语词库是从真实在售标题里提取的**词形**，模型常选同义表达
> （真实标题写 `Rollbar`，模型写 `mit Rollen`；写 `Wohnung`，模型写 `Wohnzimmer`）。
> 这个差距是真实、可解释的，比"所有指标都是 100%"可信得多。

### ⚠️ 关键词覆盖率这个指标，我一开始定错了

最早我用的是**整短语原文匹配**：把 `heavy duty tv wall mount` 当一个字符串去找。
结果是 **12%** —— 看起来文案质量很差。

但把文案摊开一看，`heavy`、`duty`、`wall`、`mount` **全都写进去了**，
标题里就有 `Heavy Duty ... Bracket` 和 `TV Wall Mount`。
**问题不在文案，在我的指标。** 搜索引擎按词（含词干）匹配，
不会要求你原样输出整个长尾短语。

所以改成了**词级覆盖**：关键词里每个实词出现在正文中的比例，再对所有关键词取平均。

> 这件事我记了很久：**指标定错了，你会朝着错误的方向优化。**
> 这是这个项目里最有价值的一条经验 —— 把度量工具的 bug 讲清楚，比报任何数字都有说服力。

### 6.2 和「真实在售文案」的对比（这一节最有说服力）

合规率只能说明"没违规"，说明不了"写得好不好"。
所以我做了一件事：**把 AI 生成的标题和你们真实在售的标题做结构化对比**
（`python compare.py`，基准存在 `data/benchmark.json`）。

**真实标题就是 ground truth** —— 它是运营真金白银在跑的文案，信息顺序、卖点取舍、
措辞风格都被市场检验过。

#### 第一次对比就发现了一个真实问题

| 样本 | 真实在售 | AI（改前） | 差多少 |
|---|---|---|---|
| Master V2 FT48 · DE | 182 字符 | 110 字符 | **短 40%** |
| Eiffel 75-100 · DE | 189 字符 | 144 字符 | 短 24% |
| Eiffel 32-75 · US | 142 字符 | 94 字符 | 短 34% |

**AI 标题系统性偏短，而且漏掉了三样东西**：系列名（Master Serie / Eiffel Serie）、
使用场景（Wohnung Büro Heim）、以及部分功能（Kabelmanagement）。

#### 改 Prompt 之后再对比

针对这个发现，我改了三处（写在 `prompts.py` 里）：

1. **充分利用字符额度** —— 目标写成上限的 90%~93%，而不是只写"不超过 200"
2. **参数里有系列名或型号，必须写进标题**
3. **至少写一个使用场景**
4. 顺带发现：**德语标题习惯用 `|` 把卖点分成 2-3 组** —— 这是从真实标题里观察到的，
   我把它写进了 `SITE_RULES["DE"]["title_style"]`

**改进前后（同一套归一化指标）：**

| 样本 | 真实长度 | AI 改前 | AI 改后 | 覆盖率 改前 → 改后 |
|---|---|---|---|---|
| Master V2 FT48 · DE | 182 | 110 | **180** | 58% → **67%** |
| Eiffel 75-100 · DE | 189 | 144 | **175** | 59% → **67%** |
| Eiffel 32-75 · US | 142 | 94 | **147** | 62% → **69%** |
| **平均** | **171** | **116** | **167** | **60% → 68%** |

**标题长度从"平均短 32%"变成"基本追平"，实词覆盖率提升 8 个百分点。**

#### 这个发现的价值

> "合规率只能说明没违规，说明不了写得好不好。所以我拿了你们真实在售的标题当基准，
> 和 AI 生成的做结构化对比。
>
> 第一次一比就发现：**AI 标题系统性偏短，平均只有 116 字符，而你们真实的是 171。**
> 短的不只是长度——它漏掉了系列名、使用场景、还有理线功能。
>
> 我改了三处 Prompt：把'不超过 200 字符'改成'目标 180 字符左右'、要求必须写系列名、
> 要求至少写一个使用场景。**改完平均长度到 167，实词覆盖率从 60% 到 68%。**
>
> 还有一个观察是你们真实标题里才有的：**德语标题习惯用 | 把卖点分成几组**，
> 这是文化习惯，不是模型能猜到的，我把它写进了站点配置。"

> ⚠️ **必须主动说的局限**：只对比了 3 条真实标题，**单个样本说明不了市场规律**，
> 要得出结论至少要 10-20 条。主动说出这一点，比假装有统计意义安全得多。

**建议做的两组对照实验：**

1. `MAX_REPAIR_ROUNDS = 0` vs `2` → 量化"定点修复"带来的合规率提升
2. 规则表述写在 System Prompt 里 vs 只放在校验器里 → 看首轮通过率差多少

## 七、已知不足（主动说，比被问出来强）

1. **文案质量没有客观指标。** 合规是机器能判的，但"有没有说服力"只能人工抽检。要量化需要找运营盲评，或做 LLM-as-a-Judge 的相对排序。
2. **关键词覆盖率只判实词是否出现，判不了"是否自然、是否堆砌、语义是否准确"。**
3. **warning 级问题不会自动修复。** 例如「后台搜索词与标题重复」这类问题，
   `evaluate.py` 会告警，但模型不会因此重写——因为 warning 需要人工判断。
   其实这一类完全可以规则化自动重写，是下一步该补的。
4. **平台规则会变**，`rules.py` 需要定期按卖家后台核对，不能一劳永逸。
5. **没有做 A+ 页面、广告文案、图片文案**——这三块是天然的下一个迭代方向。
6. **没有接真实的亚马逊接口**，目前是离线生成、人工上传。真要闭环还得对接 SP-API。

## 八、下一步迭代方向（按性价比排序）

1. **反向校验**：把已上线的 Listing 抓回来，跑一遍规则校验，找出历史违规——运营会立刻感到价值
2. **A/B 关键词版本**：同一个 SKU 生成两版标题，投广告测点击率，用数据反推哪版更好
3. **接 A+ 页面和广告文案**：同一个参数可以喂给多个模板，边际成本几乎为零
4. **接入评论数据做卖点排序**：把好评里出现最多的卖点排到五点描述的前两条
5. **多语言质量回评**：德语/日语站点可以让母语者或 LLM 做一次回译校验

## 九、一句话总结

> 这个工具的价值不在于"AI 会写文案"，而在于**它写出来的东西运营敢直接用**——
> 因为每一条都过了机器校验，不合规的会自动重写，重写不了的有兜底。
